## Abstract

리포트 지연과 연결 점유 비교는 문서 자료를 기다리는 동안 관계 저장소의 연결도 계속 점유하는지 확인하는 개발 실험이다. 실제 저장소와 동일한 연결 풀을 사용해 조회 구조와 트랜잭션 범위의 영향을 분리한다.

## Introduction

리포트가 느린 사실만으로 다른 조회의 연결 대기 원인을 확정할 수는 없다. 실험은 지연 구간에서의 연결 소유권을 먼저 확인하고, 같은 조건으로 요청을 섞어 보내 대기와 실패의 전파를 확인한다. 과거 동작은 기록을 바탕으로 재구성하며 현재 주간 감정 조회는 실제 서비스로 실행한다.

## Description

네 비교군은 날짜·세션별 반복 조회와 기간·배치 조회 각각에 전체 트랜잭션을 적용하거나 제거한다. 같은 합성 자료에서 전체 주간 응답이 같아야 한다. 성공한 단일 요청으로 조회 횟수를 비교하므로 과부하에서 일찍 실패한 요청을 조회 감소로 잘못 해석하지 않는다.

~~~mermaid
flowchart TB
    Freeze[첫 문서 조회에서 리포트들을 정지] --> Transaction{전체 트랜잭션}
    Transaction -->|있음| Held[관계 저장소 연결 소유 확인]
    Transaction -->|없음| Free[연결 비점유 확인]
    Held --> Ordinary[같은 풀의 일반 조회]
    Free --> Ordinary
    Ordinary --> Result[획득 성공·시간 초과를 비교]
~~~

별도의 혼합 부하는 리포트와 일반 조회를 독립된 일정으로 발행한다. 정상·지연 조건과 반복 순서를 고정된 규칙으로 섞고, 요청 시간·발행 지연·연결 획득과 사용 시간·실패를 남긴다. 실패한 요청도 응답 시간 분포에 포함한다. 반복별 백분위수를 평균하지 않고 원본 표본을 합쳐 비교한다.

문서 조회 지연은 클라이언트가 실제 읽기 명령을 보내기 직전의 대기다. 저장소 조회 자체는 실제로 실행하지만 서버 처리나 네트워크 지연을 직접 바꾸지는 않는다. 입력 자료와 비밀을 기록하지 않고 실행 횟수와 시간 신호만 보존한다.

선택 진단 모드는 현재 구현의 정상 조회를 반복하며 JDBC 연결 설정·실행·반환 시간을 구분한다. JVM의 소켓·잠금·정지 기록과 일회성 관계 저장소의 서버 처리 시간을 함께 수집한다. 연결 획득 실패와 실제 연결 소유자의 지연을 대조하며, SQL 원문과 환경변수는 기록하지 않는다. 추가 계측이 있는 실행은 기본 비교의 표본과 합산하지 않는다.

연결 확인의 제한 시간은 연결 획득 제한보다 짧게 유지하며 별도 회귀 검사로 확인한다. 실제 드라이버 버전과 두 제한값을 실행 조건에 남겨 과거 결과의 조건과 혼동하지 않도록 한다. 통신 지연을 좁힐 때는 드라이버 사용 여부와 저장소 접근 경로를 각각 바꾸고, 간헐적 지연을 반복 관측한다.

짧은 연결 확인에는 밀리초 제한을 적용할 수 있는 고정 조회를 사용한다. 실제 응답을 늦추는 검사를 통해 초 단위 제한으로 바뀌는 문제를 방지한다. 풀 내부의 확인 조회는 업무 조회 횟수에서 제외하고 서버 진단 자료에서 별도로 분류한다. 통신 경로 비교는 같은 실행 환경에서 동시에 수행해 전체 정지와 특정 경로의 지연을 구분한다.

실행기는 기존 자료와 분리한 일회성 관계·문서 저장소를 만들고, 소유권을 확인한 컨테이너만 종료한다. 검증용 HTTP 경로에는 운영 인증·화면 처리와 요청 전체의 영속 문맥이 없다. 과거 운영 성능이나 모든 부하에서의 무재발을 보장하는 결과로 확장하지 않는다.

실행 기록은 `.local/report/experiments/fault-runs/`, 원본 관측값은 `.local/report/experiments/fault-evidence/`에 저장한다. 경로를 옮겨도 과거 관측값과 소스 지문은 덮어쓰지 않는다.

## Conclusion

연결을 점유하는 구간, 실제 조회 횟수, 일반 조회의 대기와 실패를 함께 보아야 개선 효과를 설명할 수 있다. 이 실험은 반복할 수 있는 개발 근거를 제공하고, 각 실행의 수치는 개인 증거로 남긴다.
