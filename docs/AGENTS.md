# 문서 작성 규칙

문서는 현재 사실, 반복 가능한 절차와 결정 근거를 남긴다. 작업에 필요한 문서는 [문서 안내](README.md)에서 선택하고 코드·테스트로 현행 동작을 확인한다.

## 문서별 책임과 우선순위

| 위치 | 책임 |
| --- | --- |
| `README.md` | 목적별 탐색과 문서 링크. 다른 문서의 본문을 반복하지 않는다. |
| `PRD.md` | 사용자, 요구사항과 제품 범위. ADR이 다루지 않는 제품 범위의 기준. |
| `ARCHITECTURE.md` | 현재 구조, 신뢰 원천과 현재·과거 실행 환경. |
| `ADR.md` | 결정 당시의 이유와 트레이드오프. 설계 의도 충돌은 Accepted 결정을 우선한다. |
| `development/` | 실행·관측·검증 절차. 선택 장애 검사는 `fault-tests/`에 두고 `testing.md`에서 연결한다. |
| `runbooks/` | 증상별 확인·대응·복구. 운영 명령과 장애 대응의 기준. |
| `../.cluedoc/` | 현재 기능의 동작과 제약. API 계약은 Controller·DTO와 테스트로 확인한다. |
| 루트·하위 `AGENTS.md` | 적용 범위의 작업 규칙. 구현 경계는 아키텍처와 함께 적용한다. |

과거 결정과 현재 구현이 다르면 구분해서 적는다. 같은 규칙은 한 곳에서 관리하고 다른 문서에서는 링크한다. 구현으로 바로 확인할 수 있는 클래스 목록·설정값·일정은 작업 규칙에 복사하지 않는다.

## 설계·용어 기록

- ADR은 `docs/ADR.md` 단일 파일에 다음 `ADR-###` 번호로 추가한다. 별도 `docs/adr/`를 만들지 않는다.
- 상태는 Proposed → Accepted → Superseded 또는 Rejected이다. 결정, 이유, 버린 대안, 트레이드오프와 검증 방법을 기록한다.
- Accepted ADR은 오류 정정 외에는 다시 쓰지 않는다. 변경은 새 ADR에서 supersede하고 충돌과 재검토 근거를 적는다.
- 첫 도메인 용어가 확정될 때 루트 `GLOSSARY.md`를 만든다. 개념과 관계만 기록한다. 빈 용어집이나 `GLOSSARY-MAP.md`를 미리 만들지 않는다.
- Guide는 반복 개발 지식에만 사용한다. 낡은 안내는 삭제하거나 ADR/Runbook으로 정리한다.

## 운영 절차와 사고 기록

- Runbook 첫 문장은 `이 문서는 [알람 또는 증상]이 발생했을 때 본다.`로 쓴다.
- 명령은 dry-run 또는 읽기 전용 확인부터 제시한다. 운영 명령에는 대상 프로젝트·리전·서비스명과 rollback을 적는다.
- 비밀값 대신 이름과 저장 위치만 기록한다. 확인하지 않은 외부 API 요금·제한을 단정하지 않는다.
- 배포·인프라 변경 시 실제 대상 경로의 `AGENTS.md`와 실행 구성을 확인한다.
- 사용자 영향이나 수동 운영 개입이 있었던 사고는 원인과 재발 방지를 남긴다. 액션마다 owner·due date·검증 방법을 적고 테스트·알람·제한값·runbook 중 하나 이상으로 방어한다.

## 공유 문서와 로컬 기록

- 공유 문서는 개인 실행 기록 없이 이해할 수 있어야 한다. 공유 링크와 Cluedoc `sources`는 로컬 전용 파일에 의존하지 않는다.
- 개인 메모·실행 계획·커밋 순서·업로드 준비·실행별 검증 결과는 Git에서 제외하는 `.local/<주제>/`에 둔다. 문서는 주제 바로 아래, 코드·로그·원본 결과는 `experiments/`, 그림은 `assets/`에 둔다. `.local/docs/`는 만들지 않는다.
- 로컬 작업에서 확정된 API·제품·설계 결정은 공유 명세나 ADR에 반영한다. 실행 과정 전체를 복사하지 않는다.
- 코드 주석의 문서 참조는 안정적인 anchor를 사용한다. 문서의 코드 참조는 파일·패키지 경로로 적고 장기 문서에서 줄 번호는 피한다.
- 문서를 이동·삭제하면 상대 링크, anchor와 Cluedoc `sources`를 함께 고친다.

## 로컬 이슈

스킬의 이슈 추적기 지시는 아래 로컬 Markdown 규칙으로 해석한다. 실제 작업이 생길 때 디렉터리를 만든다.

- 기능 명세: `.local/issues/<feature-slug>/spec.md`.
- 티켓: `.local/issues/<feature-slug>/issues/<NN>-<slug>.md`. `01`부터 번호를 붙이고 티켓마다 파일을 나눈다.
- 티켓 첫 부분에 `Status: open|in-progress|blocked|resolved` 중 하나를 기록한다. triage 라벨과는 별도 상태다.
- 의존성은 같은 기능의 `Blocked by: 01, 02`, 논의는 `## Comments`, 해결·검증은 `## Resolution`에 기록한다.
- 조회는 전달받은 경로나 기능·번호로 한다. 번호만으로 기능을 구분할 수 없으면 확인한다.
- 원격 주소를 추측하거나 티켓을 자동 게시하지 않는다. GitHub 작업을 요청받으면 대상을 확인하고 기존 `github-issue-branch` 스킬과 README 규칙을 따른다.
